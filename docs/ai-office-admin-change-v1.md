# AI 비서 V1: 관리자 권한과 일정 변경 승인

PR #4 / `codex/ai-office-development`의 후속 개발 기록이다. 모든 DB 쓰기와
테스트는 로컬 합성 Supabase에서 수행한다. 운영 DB·백업·봇·환경변수·배포는
실행하지 않는다. 기존 운영 migration 및 홈페이지·SEO·CRM 액션은 변경하지 않는다.

## 관리자 권한

`supabase/dev/ai-office-admin-role.sql`의 사용자 ID 허용 목록을 사용한다.
이메일, 사용자 편집 가능한 metadata, 클라이언트 파라미터로 관리자 권한을 부여하지 않는다.
권한 부여 UI/API는 없다. 로컬 테스트 실행기만 임시 관리자 역할을 준비하고 삭제한다.
API는 검증된 Auth 사용자와 DB 관리자 등록을 모두 확인한다. DB RPC도 처리자 권한을
다시 검사하고 역할 행을 잠그므로, 검토 화면을 연 뒤 권한이 회수돼도 처리할 수 없다.
관리자 Auth 계정을 삭제해도 기존 승인 일정은 삭제하지 않으며 처리자 참조만 비운다.

일반 사용자는 일정·달력·브리핑을 읽을 수 있지만 승인·반려·합성 수신·고객 등록·
작업 생성/변경은 할 수 없다. 새 역할/감사 테이블은 anon/authenticated 직접 접근을
막는다. 중요 RPC도 service_role에만 실행을 허용하며 API가 확인한 사용자 ID를 전달한다.
service_role 자체는 신뢰 경계 내부의 고권한 자격증명이다. 브라우저에 전달하지 않는다.

기존 CRM의 authenticated 전체 쓰기 정책만으로는 일반 사용자를 막지 못하므로,
**로컬 fixture에서만** 고객·문의·작업·매출의 INSERT/UPDATE/DELETE에 restrictive
RLS를 추가했다. 기존 읽기 정책 및 관리자 CRM 기능은 유지한다. 기존 홈페이지 문의
연동의 서버 인증 경로는 보존한다. 운영 정책에 그대로 적용한 상태가 아니다.

## 변경 승인·반려

- 최신 원문과 기존 승인본을 분리한다. 미처리 변경안이 있어도 기존 승인 일정은
  달력/브리핑에서 사라지지 않는다. 신규 검토 건수와 변경 대기 건수를 따로 표시한다.
- 관리자 검토 화면에서 날짜·시간·고객·주소·작업 종류·작업 범위·금액·소요시간을
  변경 전후로 표시하고 차이가 있는 항목을 강조한다.
- 관리자는 필드를 보완한 뒤 확인 체크와 변경 승인/반려 버튼으로 처리한다.
  고객이 바뀌면 기존 고객을 검색해 명시적으로 선택한다. 후보가 없으면 관리자
  CRM 고객 등록 화면에서 등록 후 다시 선택하며 임의로 새 고객을 생성하지 않는다.
- 승인은 원문 revision, 기존 승인 revision/필드, 연결된 CRM 작업 상태를 다시
  검사한다. 승인본·같은 작업 ID의 날짜/고객/주소/범위/예상 금액·연결 snapshot·
  처리 이력을 한 트랜잭션에서 갱신한다. 고객 원장의 이름/주소를 덮어쓰지 않는다.
- 반려하면 기존 승인본과 작업을 유지한다. CRM 연결 전 변경안을 반려한 경우에도
  원래 승인본으로 작업을 생성할 수 있다. 반려된 새 금액을 쓰지 않는다.
- 원문 수정본 하나에 최종 결정 하나를 기록한다. 같은 결정 재전송은 멱등 처리하고,
  상반된 동시 승인/반려는 하나만 성공한다. 이미 결정한 revision의 재처리는 차단한다.
  재검토하려면 새 원문 revision이 필요하다.
- 기존 승인 일정과의 소요시간 겹침을 검사한다. CRM의 수동 입력 작업은 종료 시간이
  없으므로 같은 날의 미확인 작업이 있으면 보수적으로 충돌로 표시하고 자동 적용을
  중단한다. 인력별 배정/이동시간은 후속 범위다.
- CRM 작업이 수동 수정됐거나 진행/완료/매출/수납 처리된 경우 자동 변경을 차단한다.
  기존 메모 등 변경 대상이 아닌 필드는 유지한다. 일정 변경이 확정 매출이나 수납을
  만들거나 수정하지 않는다.

`ai-schedule-changes.sql`의 감사 이력은 원문 revision, 결정, 변경 전후, 처리자,
시각을 보관한다. 운영 migration과 분리된 로컬 fixture다.

## 검증

단위/수신/안전 실행기 38개, V1 HTTP·Auth·RLS·DB·CRM·모바일 통합 38개,
기존 CRM/홈페이지 문의 회귀 14개로 총 **90개** 통과.
TypeScript, ESLint, production build 및 로컬 fixture 재적용을 검증했다.

일반 사용자, 관리자 metadata 위조, 역할 자체 승격 시도, 중요 테이블 직접 쓰기,
관리자 역할 회수, RPC 처리자 재검증, 고객 변경 명시적 선택, 동시 결정, 오래된
revision, 충돌, 수동 수정/완료·수납된 CRM 보존, 반려 후 기존 승인본 연결을 포함한다.

추가 설치 없이 분리된 실제 Edge 컨텍스트에서 360/390/768/1440px를 검증했다.
기존 수신·입력·승인·수정·달력·브리핑·CRM 생성뿐 아니라 변경 전후 비교, 변경 승인으로
동일 작업 갱신, 반려 시 기존 금액 보존을 터치/클릭으로 검증했다. 외부 요청은 차단하고
합성 사용자 쿠키만 사용했다. 실물 휴대전화/OS 재부팅/운영 복구 검증을 의미하지 않는다.

합성 원문·수정 이력·승인·결정·역할·고객·작업·매출·임시 사용자는 정리한다.
로컬 UI 캡처는 Git에서 제외된 검증 폴더에만 보관한다.

## 실제 업무 전 남은 사항

운영 관리자 최초 지정/회수 담당자 확정, 기존 직원별 권한 이관 검토, 실물 모바일
검증, 수동 CRM 충돌의 관리자 해결 절차, 다중 작업 인력 및 이동시간 모델, 별도
개발 DB/Preview 검증이 남아 있다. 운영 백업·복원 검증이 미완료이므로 운영 적용을
승인한 결과가 아니다. Preview 준비는 별도 문서를 따른다.
