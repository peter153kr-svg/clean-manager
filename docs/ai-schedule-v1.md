## 연결된 흐름

`/ai-office-lab`의 일정관리 V1은 다음 흐름을 사용한다.

1. 합성 텔레그램 이벤트가 PR #1의 실제 `/api/telegram/schedule` 처리 및
   `ingest_telegram_schedule_message` RPC를 통해 로컬 수신함에 저장된다.
   화면의 합성 수신 버튼도 서버에서 같은 처리 함수를 호출한다.
   웹훅 비밀값은 브라우저로 전달하지 않는다.
2. 원문 수신 시점의 한국 날짜로 상대 날짜를 해석한다. 날짜, 시작 시간, 고객명,
   주소, 현장명, 작업 종류, 예상 금액, 소요시간을 구분한다.
   고객/주소/작업/소요시간 문자열은 시작 시간 분석에서 분리한다.
3. 누락, 복수 후보, 불명확한 오전/오후, 금액 단위 누락, 불확실/취소 표현을
   관리자 확인 대상으로 표시한다. 규칙 기반 분석이며 유료 AI API를 호출하지 않는다.
4. 관리자는 원문과 대조하며 각 필드를 직접 보완하고 승인한다.
   승인 전에는 확정 달력과 브리핑에 포함하지 않는다.
5. 승인 기록은 별도의 로컬 개발 테이블에 저장한다. 새로고침해도 유지된다.
   승인 달력은 월 이동/날짜 필터, 일정 목록을 제공한다.
   일정관리와 총괄실장 탭은 동일한 로컬 승인 데이터로 오늘/내일 브리핑을 제공한다.
   예상 금액을 확정 매출이나 수납에 합산하지 않는다.

수신함은 10초마다 갱신한다. 같은 메시지의 재전송과 오래된 수정본은 기존 RPC가
중복/역순 수신으로 처리한다. 최신 수정본은 기존 승인을 무효화하여 재검토한다.
검토 중 원문이 바뀌면 승인 RPC가 revision을 재검증하여 409로 거절한다.

## 중복·시간 충돌과 권한

화면은 다른 검토 대기/승인 일정과 동일 날짜·시각·고객·주소의 중복 후보 및
소요시간 구간의 겹침을 표시한다. 검토 대기 후보끼리는 관리자가 먼저 승인할
일정을 선택할 수 있다. 이미 승인된 일정과 겹치면 승인을 차단한다.
끝나는 시각과 다음 시작 시각이 같으면 허용하며, 자정을 넘는 구간도 비교한다.

DB RPC는 승인 트랜잭션을 직렬화하고 원문 행을 잠근다. 겹치는 두 일정을
동시에 승인하면 정확히 하나만 성공한다. 최신 revision과 reviewed 상태가
일치하는 승인만 달력에 반환한다. 모든 팀을 하나의 작업 인력으로 간주하는
보수적인 충돌 검사다. 인력/이동시간 배정은 후속 개발 대상이다.

기존 CRM 로그인 사용자가 관리자 검토를 수행하는 개발 모델이다.
새 승인 테이블과 RPC는 anon/authenticated 직접 접근을 막고 service_role만
사용한다. 별도 관리자 역할/세분화된 권한은 운영 전 설계해야 한다.
변경 API는 실제 HTTP Host와 loopback Origin을 비교한다. 실제 본문 바이트
크기도 제한하고 오류에 DB 원문/연결정보를 반환하지 않는다.

## 환경 경계 및 검증 방법

새 데이터 API는 `AI_OFFICE_DEV_MODE=synthetic`, 운영 Vercel 환경 아님,
`http://127.0.0.1:55321` 또는 `:56321` 조건을 모두 요구한다.
합성 수신 버튼은 고정 가짜 채널 `-1000000000001`만 허용한다.
운영 Supabase URL로의 연결은 새 API에서 차단된다.

`supabase/dev/ai-schedule-v1.sql`은 로컬 개발 fixture다.
`supabase/migrations` 및 운영 적용 후보 SQL에는 추가하지 않았다.
테스트 실행기는 로컬 CLI 상태를 확인한 뒤 지정된 로컬 컨테이너에만 fixture를
두 번 적용한다. 기존 6개 SQL을 재실행하거나 db push/reset을 호출하지 않는다.

검증 시 자동 환경파일을 제외한 격리 사본에서 기존 `security-local.mjs build`를
실행했다. 루트 `.env.local`을 로드하는 Next 실행은 하지 않았다.
빌드 후 같은 사본에서 다음 검증을 수행했다.

```text
node scripts/test-ai-office-local.mjs
node scripts/security-local.mjs integration
```

단위/기존 수신/안전 실행기 테스트 37개, V1 HTTP·Auth·DB 통합 테스트 14개,
기존 CRM 회귀 테스트 14개로 총 65개 통과. Next 빌드와 TypeScript 검사,
ESLint도 통과했다. fixture 적용/재적용 성공을 확인했다.
CRM 회귀는 고객/문의/작업/매출 수정, 완료 매출 생성의 중복 방지,
결제 상태·수익 보존, 삭제 제약, 익명 접근 차단, 기존 인증 화면을 포함한다.

UI에는 작은 화면에서 한 열로 배치되는 검토 폼, 줄바꿈되는 카드, 월별 달력과
최소 44px 조작 버튼을 적용했다. 실제 모바일 기기/브라우저 터치 조작 검증은
아직 하지 않았다. 자동 HTTP 검증과 빌드는 브라우저 E2E 테스트를 대체하지 않는다.

합성 테스트용 원문, 승인 기록, 임시 Auth 사용자는 테스트 종료 시 정리한다.
개발 fixture 스키마와 로컬 컨테이너 볼륨은 다음 검증에 재사용할 수 있다.

## 아직 연결되지 않은 부분과 다음 작업

- 실제 텔레그램 봇/웹훅 활성화와 외부 메시지 발송은 하지 않았다.
- V1 승인 일정은 기존 CRM 고객·작업·매출 테이블에 쓰지 않는다.
  고객 매칭/작업 생성의 중복 방지와 취소·재승인 이력이 다음 개발 대상이다.
- 이전 메모리 기반 직원 실험 화면은 접힌 영역/별도 매출·콘텐츠 탭에 보존하며,
  V1 승인 데이터와 분리되어 있음을 표시한다.
- Vercel Preview/별도 호스팅 개발 DB는 미연결이다. 현재 V1 데이터 API는
  loopback 전용이므로 Preview 연결은 별도 개발 DB와 인증 검토가 필요하다.
- 운영 DB 접속·마이그레이션·백업 재실행·배포는 수행하지 않았다.
  운영 적용 SQL/권한 설계, 검증된 운영 백업/복구 조건, 실제 봇 설정은
  후속 별도 승인 대상으로 남긴다.
