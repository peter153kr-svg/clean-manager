## 범위

PR #4 / `codex/ai-office-development`의 후속 개발이다. PR #1 브랜치와 main은
수정하지 않는다. 운영 백업은 미완료 상태이며 이번 작업에서 재실행하지 않았다.

## CRM 연결

기존 `customers`의 이름·필수 연락처·주소 및 `jobs`의 고객 FK·날짜·시작 시간·
작업 종류·주소·현장·예상 금액을 재사용한다. 기존 테이블 정의, 홈페이지·SEO,
CRM 서버 액션 및 운영 SQL은 변경하지 않았다.

승인된 일정의 고객명 또는 주소와 일치하는 기존 고객을 검색한다(공백·대소문자
정규화). 한 명이어도 자동 선택하지 않는다. 여러 후보는 이름·연락처·주소를
나란히 보여 주고 관리자가 선택한다. 후보가 없을 때만 이름·주소를 채운 신규
등록 초안을 제시하며 연락처를 별도로 입력해야 한다. 확인 체크와 생성 버튼을
모두 거쳐야 고객/작업이 생성된다. 후보가 있거나 같은 연락처가 존재하면 신규
등록을 거절한다. 연락처가 없는 고객을 임의의 번호로 등록하지 않는다.

`supabase/dev/ai-schedule-crm-v1.sql`은 로컬 fixture이며 운영 migration 목록에
추가하지 않는다. 새 링크 테이블에 원문 ID·revision·승인 필드 snapshot·고객·작업·
처리자를 기록한다. RPC는 기존 승인과 같은 트랜잭션 잠금을 사용한다.

- 최신 승인 revision 및 필드 snapshot을 다시 검사한다.
- 고객 생성, 작업 생성, 링크 저장을 하나의 트랜잭션으로 수행한다.
- 동일 일정 재클릭/동시 요청은 같은 작업 ID를 반환한다.
- 서로 다른 메시지의 같은 신규 고객 동시 등록도 중복 생성하지 않는다.
- 이미 있는 동일 고객·날짜·시간·주소의 작업 후보는 자동 중복 생성하지 않는다.
- 예상 금액만 저장하며 작업 상태는 scheduled, 확정 금액은 NULL이다.
  매출과 수납 레코드를 생성하지 않는다.

텔레그램 원문 수정은 기존처럼 승인을 무효화한다. 작업 링크는 보존하고 재검토
경고와 기존 CRM 작업 링크를 보여 준다. 재승인해도 기존 작업을 자동으로 삭제하거나
덮어쓰지 않는다. 이미 연결된 작업의 변경 적용은 CRM에서 별도로 검토해야 한다.

기존 CRM 자체에는 고객 이름/연락처의 전역 unique 제약이 없다. 이번 중복 방지는
AI 작업 생성 RPC를 통해 들어오는 요청과 당시 존재하는 CRM 작업을 대상으로 한다.
다른 CRM 입력 경로 전체에 새 unique 제약을 강제하지 않았다.

## 인증 및 환경 경계

CRM API도 synthetic 모드·loopback Supabase URL·로그인을 요구하고 실제 HTTP Host와
Origin을 대조한다. JSON 본문은 16KiB로 제한한다. 관리자 확인이 없으면 생성하지 않는다.
일반 authenticated/anon 역할의 새 테이블 직접 접근 및 RPC 실행을 차단한다.
현재는 기존 CRM과 같은 로그인 직원 권한 모델이며 운영 전 별도 관리자 역할 설계가 필요하다.

## 실제 브라우저 검증

추가 설치 없이 기존 Microsoft Edge를 Playwright의 분리된 컨텍스트로 실행했다.
실제 브라우저 엔진에서 viewport와 터치를 에뮬레이션했으며 실물 휴대전화 검증은 아니다.
브라우저 요청은 localhost/127.0.0.1만 허용하고 외부 요청을 차단했다.
임시 합성 Auth 사용자 쿠키만 사용하고 개인 브라우저 프로필/로그인 정보는 사용하지 않는다.

| 화면 | 검증 |
| --- | --- |
| 360×800 | 터치, 입력, 승인·수정, 달력 이동/필터, 브리핑, CRM 신규 초안·확인·생성, 새로고침 |
| 390×844 | 위와 동일 |
| 768×1024 | 태블릿 터치로 위와 동일 |
| 1440×1000 | PC 클릭으로 위와 동일 |

네 화면 모두 document scrollWidth가 viewport 이내임을 확인했고 브라우저 pageerror가
없었다. 실제 스크롤을 거쳐 카드·폼·달력·브리핑을 조작했다. 360px와 PC 전체 화면
캡처를 시각적으로도 확인했다. 기본 44px 버튼과 줄바꿈 폼을 유지하고, 보고 기준일
입력과 달력 필터 조작부의 높이를 보완했다. 보고 기준월을 바꿀 때 달력도 같은
기준월을 따르도록 수정했다. 화면의 CRM 연결 안내도 실제 로컬 연결 상태에 맞췄다.

## 검증 결과

- 기존 단위/수신/안전 실행기 테스트 37개.
- V1 HTTP·Auth·DB·CRM·Edge 화면별 E2E 및 앱 재시작 테스트 27개.
- 기존 CRM 및 홈페이지 문의 API 회귀 14개.
- 총 78개 통과, TypeScript·ESLint·production build 통과.
- 로컬 fixture 적용/재적용 검증. 고객 다중 후보, 관리자 미확인 거절, 연락처 중복,
  동일/다른 메시지 동시 생성, 수동 기존 작업 중복, 수정본 재검토, 원작업 보존,
  익명 접근·직접 RPC 접근 차단을 포함한다.
- 브라우저 새로고침 및 Next 서버 종료/재시작 뒤 승인·연결·작업 보존을 확인했다.
  OS 재부팅/DB 장애 복구 검증을 수행한 것은 아니다.
- 합성 원문·수정 이력·승인·링크·고객·작업·매출·Auth 사용자는 종료 시 정리한다.

## 실제 서비스 적용 전 남은 작업

별도 호스팅 개발 DB와 Vercel Preview, 실제 기기/키보드·스크린리더 검증, 변경된
일정과 기존 작업의 차이 비교·관리자 적용 이력, 관리자 역할 분리, 운영용 SQL 및
복구 조건 검토가 남아 있다. 고객 후보는 현재 이름/주소 기반이며 전화번호 추출·
동명이인 식별 보강이 필요하다. 실제 봇 활성화·운영 DB 변경·main 병합·운영 배포는
수행하지 않았다. 운영 백업/복원 검증이 미완료이므로 운영 적용 승인을 의미하지 않는다.
